# Resync（整链恢复）设计与验收 · 2026-11-15

**对应任务** `#33`（090-01 同步恢复）· 062-02 契约的增量
**协议** Sync Protocol v3 的**新增能力**（不改现有字段，旧客户端忽略即可）
**动机** 审计 062-01 G3：全仓没有 resync/snapshot 端点，Core 的 `Invalid sync cursor` 被映射成 `invalid_response` 后客户端进入 blocked，用户无法自救。`rejected` 条目（`engine.py:113`）也没有任何出边。

---

## 1. 现存的三个硬约束（决定了设计形状）

| 约束 | 位置 | 影响 |
| --- | --- | --- |
| 拉取要求 `revision == cursor + 1`，不允许跳号 | `engine.py:175` | 快照不能"重放历史"，必须直接给状态 |
| 每条变更一个事务，业务行/冲突/cursor 同一提交 | `engine.py:234` | 快照应用也要保持"一实体一事务 + cursor 同提交"或"整批一事务" |
| `item.sync_revision` 是下一次 push 的 `baseRevision` | `engine.py:212` | 快照必须携带**实体级** `syncRevision`，不是日志 revision |

## 2. Core：快照端点

```
GET /api/v1/sync/snapshot?protocolVersion=3&cursor=<opaque>&limit=200
Authorization: Client credential (nc_live_*)
```

**分页**：keyset 分页，`cursor` 是上一次响应里的不透明值（`entityType|entityId` 的 base64url），首次请求省略。

响应：

```json
{
  "protocolVersion": 3,
  "snapshotId": "0f7c…",
  "workspaceRevision": 1234,
  "entities": [
    {"entityType": "website", "entityId": "…", "syncRevision": 42,
     "deleted": false, "data": {"name": "…", "url": "…"}}
  ],
  "cursor": "d2Vic2l0ZXx…",
  "hasMore": true
}
```

| 规则 | 内容 |
| --- | --- |
| 一致性 | 在 workspace 行锁内读取：先锁 `SyncWorkspaceState`，记录 `workspaceRevision`，再按 keyset 扫实体 |
| 范围 | 9 种实体全量；**包含墓碑**（`deleted: true`，`data: null`），这样本地能识别"远端已删" |
| 大小 | 每页 ≤ `limit`（默认 200，上限 500）；个人规模通常一页够 |
| 幂等 | 纯读，可重复调用；`snapshotId` 标识一次逻辑快照（首请求生成，分页时带 `snapshotId` 复用，避免跨页漂移） |
| 认证 | 与 `/changes` 相同：Client 凭证，工作区从凭证派生 |
| 版本 | `protocolVersion != 3` → `409 sync_protocol_mismatch` |

**跨页一致性**：首请求生成 `snapshotId` 并把 `workspaceRevision` 固定；后续分页请求带上 `snapshotId`，Core 用该 revision 过滤（`entity.sync_revision <= workspaceRevision`），保证分页期间新增的行不会撕裂。

**缺失 ≠ 删除（关键规则）**：因为快照是"截至 R 的状态"，一条**在 R 之后被更新**的实体会被过滤掉（它的 `sync_revision > R`），但它并非被删除 —— 它在 R 时仍然存在。因此客户端恢复时：

- 只按快照里的**显式墓碑**（`deleted: true`）删除本地行；
- 本地有、快照里没有的行**一律保持原样**，不得标删；
- 这些行会由随后的 `/changes?cursor=R` 自然补齐（它们的变更 revision 必然 > R）。

若把"缺失"当删除，恢复会瞬间误删所有在翻页期间被编辑过的实体，再被下一次拉取还原 —— 表现为数据闪断甚至级联删除。


### 2.1 cursor 失效的可识别错误

`GET /changes` 在 `cursor > workspaceRevision` 时，从现在的纯文本改为：

```json
{"detail": "Invalid sync cursor", "resyncRequired": true, "workspaceRevision": 1234}
```

保留 `detail` 字面量（兼容现有断言/日志），新增两个字段。客户端据此进入恢复流程，而不是 `invalid_response → blocked`。

## 3. Local：恢复流程

```
POST /api/v1/sync/resync        (Local 模式, 用户 JWT)
```

单次调用内完成（持有 workspace 锁，与同步周期互斥）：

1. **取快照**：翻页直到 `hasMore=false`，得到 `workspaceRevision = R`。
2. **逐实体应用**（沿用现有冲突语义，不静默覆盖本地编辑）：
   - **快照 `deleted: true`** → 本地行标删除；若存在 pending 条目，转 conflict（`currentRevision = syncRevision`）。
   - **快照 `upsert`** → 应用 `data`，`sync_revision = syncRevision`；若本地有 pending 条目 → 不覆盖本地业务行，转 conflict（与 `engine.py:192-211` 同语义）。
   - **本地存在但快照里没有** → **保持原样，不得标删**（见 §2「缺失 ≠ 删除」）。这类行要么是在 `R` 之后被更新、要么是仅存在于本地的未推送编辑，两者都会由随后的 `/changes?cursor=R` 或 push 收敛。
3. **推进 cursor = R**，与第 2 步同一事务提交。
4. **保留 outbox**：不删任何 `pending/in_flight/conflict` 条目。它们的 `base_revision` 不变，下一次 push 会自然产生 conflict，由 Conflict Center 呈现（**绝不静默丢弃本地编辑**）。
5. 返回：`{"workspaceRevision": R, "applied": n, "deleted": n, "conflicts": n, "pending": n, "cursor": R}`。

**自动触发**：同步周期若收到 `resyncRequired`，暂停本轮、把状态置为 `resync_required` 并记录 `last_error`；**不自动重建**（快照可能很大，且用户可能正在编辑）—— 由 UI 提示并提供"重新同步"按钮；Android 侧同理。

**并发**：整个流程持有 `_lock_for(db_url, workspace_id)`（与 `resolve_conflict` 同一把锁，10s 上限等待，参照 `conflicts.py`）。

## 4. `rejected` 条目的出口（同批修复）

`rejected` 目前只会永久阻塞后继（`engine.py:273-293`）。加两条最小出口：

| 动作 | 端点 | 语义 |
| --- | --- | --- |
| 放弃 | `POST /api/v1/sync/rejected/{id}/dismiss` | 条目置 `resolved`，依赖它的后继标记 `skipped`（不再等待） |
| 重投 | `POST /api/v1/sync/rejected/{id}/retry` | 用户修正本地数据后，用**新 mutationId** 与原语义重建一条 pending，原条目置 `resolved` |

两者都要求 Local 模式 + 用户 JWT，且在 workspace 锁内执行。

## 5. 验收（必须逐条有证据）

| # | 场景 | 通过条件 |
| --- | --- | --- |
| R1 | Core revision 归零后本地 cursor 超前 | `/changes` 返回 `resyncRequired`，本地状态为 `resync_required`，**不**丢 outbox |
| R2 | 手动 resync（本地有 pending 编辑） | 快照应用后 cursor = R；pending 保留；后续 push 产生 conflict 而非静默覆盖 |
| R3 | 快照含墓碑 | 本地对应行被标删；UI 不再显示 |
| R4 | 分页 | `limit=1` 强制多页，最终状态与单页一致；跨页一致性不撕裂 |
| R5 | rejected dismiss | 后继不再永久等待；`status` 汇总里 rejected 归零 |
| R6 | rejected retry | 新 mutationId 重投成功；原条目 resolved |
| R7 | 并发 | resync 与同步周期不会同时跑（锁）；10s 内拿不到 → `409 sync_in_progress` |
| R8 | 大工作区 | 500 实体分页恢复耗时 < 5s（本机 SQLite + PG 各一次） |
| R9 | 缺失 ≠ 删除 | 实体在 `R` 之后被更新 → 快照里没有它 → 本地行**不得**被标删，且 `/changes?cursor=R` 后数据收敛 |
